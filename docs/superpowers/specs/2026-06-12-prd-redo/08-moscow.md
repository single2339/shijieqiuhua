# 世界球花 — MoSCoW 优先级排序

## Summary

输入 **107 条修订后基线**（94 - DUP 3 + GAP 16，详见 07-gap-audit），按 MoSCoW 排序：

| 档 | 计数 | 含义 |
|---|---|---|
| **M (Must)** | 90 | v1 上线必须有；缺一条则不能上线 / 不合规 / USP 失效 |
| **S (Should)** | 15 | 应该做；v1 时间允许就做，否则优先 v1.1 |
| **C (Could)** | 0 | v1 不规划；如 v1 工期富余可以临时拣 S 当 C |
| **W (Won't this time)** | 2 | 显式延后到 v1.5+ |

> 90 条 M 看起来多，但其中约 30 条已经实现或半实现（修复 PR 后），25 条是修订/校验已有逻辑，35 条才是新写——工程量约 60 个工作单元，单人 4-6 周可达成。

## 假设

- 总工期目标：v1 上线于 2026-07-25 ± 1 周（4-6 周开发）。
- 工程量估算粒度：粗略，准确数字阶段 4 用例规格 + 阶段 5 PRD 时再细化。
- "Must" 的判定基准：失去该条 = 触发以下之一：
  - USP 失效（U-1 证据链 / U-2 不编造）
  - 商业模式失效（邀请 + 付费码闭环）
  - 合规 / 法律红线被踩
  - 不可用（< 99% SLO 的运维基础）

## 范围扩张防御

为防止"项目过程中又把 W 拉回 M"的常见失败模式：

1. **任何把 W → M 的变更**：必须先在 `decisions.md` 追加新决策记录，写明影响（如工期延长、其他 M 降级）。
2. **任何 S 自动升 M**：禁止；只能"S 完成有富余 → 拣 C"，不允许"S 升 M"。
3. **新增需求**：默认进 v1.1 队列；只有触发 USP / 红线 / 合规时才进 v1。
