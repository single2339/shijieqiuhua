# 世界球花前端设计规格

日期：2026-06-11

## 目标

将现有足球预测应用升级为“世界球花”：一个微信小程序优先、Web 增强的足球情报预测产品。

核心体验不是单纯预测胜负，而是围绕每场比赛持续问答。用户可以快速查看默认赛前判断，也可以继续追问半场、红黄牌、角球、进球数、球员状态、临场风险等具体问题。

## 设计假设

- 用户主要在微信里快速查看今日赛事，因此小程序体验优先。
- Web 端用于更深的研判、连续分析多场比赛、查看历史报告和复盘，不强行复刻小程序布局。
- 产品不使用市场价格模型，不输出保证式结论；界面文案使用“倾向、压力、风险、证据强弱”等表达。
- 小程序分享和订阅消息必须遵守微信平台约束：分享由用户触发，订阅消息需要用户主动授权。

## 品牌方向

品牌名：世界球花

定位：有记忆点的足球情报助手，而不是冷冰冰的赛果预测器。

视觉方向采用“绿茵纸感”：

- 主色：深绿，用于品牌、主判断卡、关键按钮。
- 辅色：草金，用于可信度、概率环、重点提示。
- 背景：暖纸色，降低体育数据产品的冰冷感。
- 字体：沿用当前 Web 技术栈里的高质量无衬线字体方向，中文界面保持清晰、紧凑、可信。
- 图标：正式实现时使用已有 `@phosphor-icons/react` 或跨端可复用的本地图标，不使用 emoji 作为产品 UI。

## 信息架构

### 微信小程序

小程序采用 4 个底部 Tab。

1. 今日
   - 默认首页。
   - 展示今日和明日重点赛事。
   - 每场显示比赛问答卡摘要：默认倾向、可信度、风险数量、可追问入口。
   - 提供联赛、时间、关注状态筛选。

2. 情报
   - 聚合所有比赛相关信号。
   - 分类包括伤停、战意、赛程、地理体能、裁判、天气、舆情。
   - 支持从情报信号跳转到受影响比赛。

3. 报告
   - 保存用户生成过的问答结果和赛前长报告。
   - 支持收藏、赛后复盘、分享海报。

4. 我的
   - 管理关注比赛、订阅提醒、邀请权益、账户偏好。
   - 放置免责声明和产品边界说明。

### Web

Web 端使用同一套数据模型，但布局升级为工作台。

- 左栏：赛事队列，展示联赛、时间、关注状态、风险变化。
- 中栏：宽屏版比赛问答卡，展示默认判断、维度评分、证据摘要。
- 右栏：Ask 面板，保留用户问题历史、推荐追问、证据引用和报告生成入口。

## 核心组件

### MatchQuestionCard

比赛问答卡是“世界球花”的核心组件。

结构：

1. 比赛头部
   - 联赛、开赛时间、主客队。
   - 显示中立场、天气、临场风险等状态。

2. 默认主判断
   - 默认展示胜平负或方向倾向。
   - 展示可信度分数、评级和风险提示。
   - 仍保持快速浏览能力，避免用户必须先提问才获得价值。

3. 继续问输入框
   - 标题为“继续问这场比赛”。
   - 输入框自动绑定当前 `match_id`。
   - 用户无需重复描述比赛上下文。
   - 支持自由问题，例如“上半场角球会不会偏多？”。

4. 快捷问题 chips
   - 半场
   - 红黄牌
   - 角球
   - 进球数
   - 球员
   - 风险

   这些 chips 是分析维度入口，不是投注玩法承诺。点击后生成带上下文的问题，并提示用户可继续编辑。

5. 证据摘要
   - 显示强证据、弱信号、样本不足三类内容。
   - 每条证据保留来源或来源类型。
   - 结论必须能解释“为什么”。

### EvidenceStrength

用于统一展示证据强弱。

- 强证据：多源一致、近期、直接影响比赛。
- 弱信号：单源、间接影响、样本较小。
- 样本不足：当前无法支撑明确结论。

### SharePoster

用于生成可分享的赛前卡片。

必须包含：

- 比赛双方和开赛时间。
- 用户问题或默认主判断。
- 可信度等级。
- 关键证据和风险提示。
- “世界球花”品牌名。
- 产品边界说明：情报研判，不保证结果。

## 数据流

1. 赛事数据
   - `match_id`
   - 联赛、球队、开赛时间、状态。

2. 情报数据
   - 伤停、战意、赛程、地理体能、裁判、天气、舆情。

3. 用户问题
   - 自由输入或快捷 chips 生成。
   - 与当前 `match_id`、已有比赛情报、问题维度一起提交。

4. 分析服务
   - 后端返回结论、可信度、证据、风险、报告正文。
   - 如果证据不足，返回“不确定”或“样本不足”，而不是强行给方向。

5. 展示和留存
   - 小程序展示问答结果。
   - 报告页保存历史结果。
   - 用户可收藏、分享、订阅临场变化。

## 微信小程序约束

- 顶部导航必须避开微信右上角胶囊按钮和安全区。
- 底部 Tab 应通过小程序全局配置承载，保持原生预期。
- 分享能力由用户触发，分享卡片不应夸大确定性。
- 订阅消息只在用户关注比赛或点击提醒时请求授权，不做静默推送假设。

- 小程序全局配置与 `tabBar`：https://developers.weixin.qq.com/miniprogram/dev/reference/configuration/app.html
- 分享能力：https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/share.html
- 订阅消息：https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/subscribe-message.html

## 跨端实现边界

正式实现时不要把 Web 页面直接压缩成小程序页面。建议分层：

- 领域模型：比赛、情报、问题、证据、报告。
- 领域组件：比赛问答卡、证据强弱、快捷问题、报告正文。
- 平台壳层：小程序导航、Web 工作台布局。

Web 端可先在现有 React/Vite 项目里完成品牌与组件改造。小程序端建议后续选择 Taro、uni-app 或原生小程序实现；本设计不强制技术栈，但要求共享接口契约。

## 成功标准

- 用户打开首页后，无需搜索即可看到今日重点赛事和默认判断。
- 用户能在首屏或接近首屏的位置继续追问当前比赛。
- 半场、红黄牌、角球、进球数等问题被作为核心入口呈现。
- 每个回答都能看到证据强弱和风险提示。
- 小程序和 Web 使用一致的数据语义，但采用不同布局。
- 分享和订阅能力符合微信平台约束。
- UI 不使用 emoji 作为正式图标，不出现保证结果或诱导式文案。

## 非目标

- 不在本阶段实现支付、会员、邀请返佣的完整商业化闭环。
- 不在本阶段承诺接入真实赔率、盘口或市场价格模型。
- 不在本阶段重构后端预测算法。
- 不在本阶段同时交付完整微信小程序代码。

## 后续实施建议

1. 先改造现有 Web 前端品牌和核心比赛问答卡。
2. 抽出前端领域类型和组件边界，避免所有逻辑继续堆在 `App.tsx`。
3. 补充问题维度到请求结构，支持半场、红黄牌、角球、进球数等上下文。
4. 增加小程序适配设计稿或跨端技术选型。
5. 在有稳定接口后，再实现小程序端。
