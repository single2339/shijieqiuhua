# 世界球花 — 业务问题框定

## 1. 业务情境与触发器

### 1.1 当前状态（事实）
- 已有可运行的 OSINT 网络（`osint-network` 主项目），8 大情报层，FastAPI + React 19 + DeepSeek。
- `shijieqiuhua` 子项目作为足球预测产品分支已上线 MVP 骨架：
  - 后端：`backend/football_osint/`（pipeline + 路由 + Win007 模板源），跑通零配置预测路径，12 个 pytest 通过。
  - 前端：单文件 `App.tsx` + `MatchQuestionCard`，调 `/api/football/osint/answer` 取一个简化判断。
- 部署目标：足球服务器 `221.239.50.142:31080`（已在 `.agents/memory/deployment-targets.md` 备案）。

### 1.2 已有规格（设计意图）
- `docs/superpowers/specs/2026-06-11-shijieqiuhua-frontend-design.md`：完整定义品牌、4 Tab 小程序、Web 工作台、9 个组件、邀请 + 付费访问门、统一账号模型、跨端边界。
- `docs/superpowers/specs/2026-06-11-shijieqiuhua-osint-football-redesign.md`：定义后端 OSINT 模块拆分（10 子模块）、动态因子注册表、证据契约、零配置采集策略、4 个 Job API。

### 1.3 触发器
2026-06-11 的 commit `8c09e12 feat: build Shijieqiuhua web MVP` 把前端从 spec 描述的"多组件 + 访问控制 + Tab"压回了"单页 mock + 一个问答卡"，并删除了：
- `frontend/src/shijieqiuhua/access.ts`（访问控制状态机）
- `frontend/__tests__/shijieqiuhua-access.test.ts`（访问控制测试）

后端 `pipeline.py` 中出现了哈希伪造的"近期状态信号"（`_stable_bias` sha1）和被当成证据的"采集计划"占位项；`/api/football/osint/*` 落入 `_PUBLIC_PREFIXES`，匿名可访问。

代码审查（2026-06-12）已修复 SRF、资源耗尽、内存泄漏、伪造证据等技术债，但暴露出**产品方向、范围与交付优先级未对齐**的根本问题。本次 PRD 重梳即为该问题的应对。

## 2. 症状 vs 根本原因

| 症状（可观察） | 直接原因 | 根本原因（待验证） |
|---|---|---|
| 9 个 spec 组件只交付 1 个 | App.tsx 没拆，组件库未建立 | MVP 边界不明 → "全交付"不可能时工程师默认选最少 |
| 访问控制被删 | `b0fe804` commit 加了，`8c09e12` commit 又删了 | "邀请 + 付费"是约束还是 MVP 必需未对齐 → 实施期被当成可选 |
| pipeline.py 单文件 685 行 | spec 的 10 子模块拆分未做 | spec 写得过于详细，但没标必须做的最小集 → 拆分变成"以后再说" |
| 用 sha1 伪造预测倾向 | `form.recent_signal.impact = query_bias × 0.08` | "证据优先"原则与"必须给方向"产品压力冲突 → 缺数据时降级路径未定义 |
| `/api/football/osint/*` 公开 | `_PUBLIC_PREFIXES` 包含 `/api/football/` | 当前阶段对未登录用户的预测端点曝光程度未规定 |
| 访客/已注册未付费/已付费三层权限缺失 | 后端无权限分层，前端无 AuthGate | 收费模式（邀请 + 付费 vs 试用 vs 全开放）未做最终决策 |
| 微信小程序未开工 | 单文件 React Web | 跨端阶段（先 Web 还是同时上小程序）未拍板 |

### 2.1 三个核心断层
**断层 A — 商业模式断层**：访问控制（邀请+付费）写进了 spec，但 commit 历史显示反复删改。这表明产品方对"是否第一版就收费"没有最终决策。如果不收费，spec 中所有"已注册未付费/已付费"分支都是死代码。

**断层 B — 范围/优先级断层**：spec 列出 9 个组件、10 个后端模块、4 个微信小程序 Tab。没有任何"M/S/C/W"或"P0/P1/P2"标注。工程师在时间压力下被迫自行选择最小集，结果不一致。

**断层 C — 预测原则与产品压力的断层**：spec 第 12 行强调"证据优先，每个预测结论都能追溯到证据"，但当无证据时，前端仍要展示"主队倾向"——产品压力倒推出哈希伪造。需要明确：缺证据时是 (a) 不显示倾向，(b) 显示"信息不足"，还是 (c) 接受弱信号但标注？

## 3. 目标、期望结果与成功标准

### 3.1 业务目标（北极星）
**让懂球但不懂数据的用户，在每场比赛前能用 1 分钟拿到一份带证据链的研判简报，并能继续追问关键维度。**

研判 ≠ 预测胜负。重点在"证据强弱 + 风险维度 + 不确定性"。

### 3.2 期望结果（outcome，非功能）
1. **可信度**：用户感受到"这个判断是有理有据的"，而不是"看起来很玄"。
2. **可继续性**：用户用完默认主判断后，能自然地追问 ≥ 1 个具体维度。
3. **跨端一致**：同一用户在 Web 和（未来）小程序看到的结论一致。
4. **可商业化**：访问控制和付费链路是真实可用的，不是 mock。
5. **可审计**：每条结论都能回溯到证据 ID 和源采集时间，便于事后复盘。

### 3.3 成功标准（可度量）
- **MVP（v1）**：
  - 已付费用户从打开赛事到看到带 ≥3 条证据的主判断，耗时 < 5 秒。
  - 默认主判断在缺证据时**明确显示"信息不足"**而不是给方向。
  - 邀请码注册 → 付费/兑换码 → 完整功能开通的端到端链路在 Web 通跑。
  - 自由提问命中比赛上下文的判定（`_is_match_related`）召回率 ≥ 90%（基于人工标注 50 条样本）。
  - `pytest tests/test_football_osint.py` 全过；`npm run build` + `vitest` 全过。
- **v1.5**：
  - 微信小程序壳交付（4 Tab）+ 跨端账号合并跑通。
  - 每天能完成 ≥ 200 场比赛的赛前研判落盘（不含临场更新）。
- **v2**：
  - 已付费用户 7 天留存 ≥ 30%。
  - 邀请-注册-付费转化漏斗各级数据可观测。

## 4. 假设、约束与不可妥协项

### 4.1 假设（待验证）
| ID | 假设 | 验证方式 |
|---|---|---|
| A1 | 用户愿意为"带证据的研判"付费，而不是只为"赛果预测"付费 | 上线后 7 天看付费率 |
| A2 | "邀请码 + 付费"门槛不会扼杀冷启动；早期用户主要靠定向邀请 | 邀请-注册转化率 ≥ 50% |
| A3 | 微信小程序是核心入口（spec 假设），Web 是工作台 | 上线后看小程序 vs Web DAU 比 |
| A4 | 公开网站 + Win007/球探基本面，足够支撑赛前研判 | 内部对 50 场比赛人工评估证据充分度 |
| A5 | 用户不会要求实时（比分、滚球）；只看赛前 | 用户访谈 |

### 4.2 约束（外部不可改）
- **C1 法律/合规**：仅采集合法公开数据；微信小程序须遵守平台条款（订阅消息、分享、支付）。
- **C2 微信平台**：`session_key` 不下发；分享必须用户触发；订阅消息必须用户授权。
- **C3 部署**：足球服务器单机 `221.239.50.142`，无 K8s，无独立数据库，bronze JSON + 内存缓存。
- **C4 LLM**：DeepSeek API（`LLM_API_KEY`），不能依赖付费足球数据 API（无预算）。
- **C5 工程**：单人开发节奏，前端 React 19 + Vite，后端 FastAPI + Pydantic v2。

### 4.3 不可妥协项（产品红线）
- **R1 不输出投注建议**。所有文案使用"倾向、压力、风险、证据强弱"。
- **R2 不在缺证据时编造倾向**。哈希伪造、随机方向、市场默认值——一律禁止。
- **R3 不绕过付费**。客户端"支付成功"提示不开通权益；只信服务端回调或服务端兑换。
- **R4 不在前端硬编码秘密**。`session_key`、付费码、API 密钥永远在服务端。
- **R5 邀请关系仅用于注册准入和增长统计**，不影响预测结论或证据展示。

## 5. 范围边界（in / out）

### 5.1 在范围内（v1 MVP）
| 模块 | 内容 |
|---|---|
| 用户与权限 | 邀请码注册、邮箱/手机号登录、付费 + 付费码、3 级权限分层（访客/已注册未付费/已付费） |
| 核心研判 | 每场比赛默认主判断 + 自由提问 + 6 维快捷追问（半场、红黄牌、角球、进球数、球员、风险） |
| 证据系统 | 证据强弱（强/弱/不足）三级展示 + 来源回溯 + 缺数据明示 |
| 后端 OSINT | Win007 公开页面、用户补充 URL（白名单）、用户补充笔记、零配置采集 |
| Web 工作台 | 三栏布局（赛事队列 / 比赛卡 / Ask 面板） |
| 部署 | 单机 + nginx + systemd，bronze JSON 持久化 |
| 测试 | pytest（后端 OSINT 流水线）+ vitest（前端关键路径） |

### 5.2 范围外（明确不做）
| 模块 | 原因 | 后续阶段 |
|---|---|---|
| 微信小程序代码 | 单人开发节奏，先稳 Web | v1.5 |
| 实时/滚球分析 | 数据源不支持 | v2+ |
| 真实赔率/盘口接入 | 无预算，且与"不输出投注建议"原则冲突 | 可能永不做 |

| 重构 osint-network 主项目 | 与本 PRD 解耦 | 独立项目 |

### 5.3 灰色地带（待决策）

- v1 是否要落"分享海报"？

## 6. 候选解决方向

| 方向 | 描述 | 优势 | 劣势 |
|---|---|---|---|
| **D1：MVP 收紧** | 砍小程序、砍邀请系统、砍付费，做"开放访问 + 极简 Web"，先验证研判价值 | 最快上线，最小工程 | 失去 spec 中的商业模式；后续加回成本高 |
| **D2：对齐 spec 但分期** | 完整保留 spec 设计，但 v1 只做"Web + 已付费功能流"，访问控制走"硬编码白名单" | 不丢 spec 长期方向；架构提前布好 | 邀请/付费链路是假的，用户不能自助 |
| **D3：对齐 spec 完整 v1** | spec 全做（邀请 + 付费 + 9 组件 + Web + 小程序壳） | 商业模式上线即真 | 工期 3-4 倍；单人扛不住 |
| **D4：双轨**（推荐） | Web v1 = 已付费功能 + 真实邀请/付费链路；微信小程序 v1.5；研判核心永远不前置访问控制（让访客也能看公开摘要） | 商业模式真实可用；工程量可控；微信端不卡死整体节奏 | 需要明确 v1 vs v1.5 的交付边界，并且必须立即做账号模型 |

## 8. 推荐框定与未解决问题

### 8.1 推荐方向：**D4 双轨**

**核心定位（一句话）**：
> 世界球花是一个"带证据链的足球研判工作台"——给懂球但不擅长读数据的用户，提供赛前判断、可追问的维度分析和证据强弱标注，不输出投注建议。

**MVP 形态（v1）**：
- 平台：仅 Web。
- 用户体系：邀请码注册 + 付费/付费码兑换 + 3 级权限，**链路必须真实可用**。
- 核心组件：MatchQuestionCard（已付费完整版 + 未付费降级版）、EvidenceStrength、AuthGate、AccountStatus、PaymentUnlock、InvitePanel（共 6 个组件，是 spec 9 个的子集）。
- 后端：在已有 `football_osint/` 上做模块化拆分（最少：拆出 `factor_registry.py` 和 `analysis/` 子目录），保留单进程部署。
- 预测原则：**证据不足时显示"信息不足"，绝不编造倾向**（直接砍掉 v1.5 才接的"市场倾向"占位）。

**v1.5 形态**：
- 加微信小程序（4 Tab）。
- 跨端账号合并（unionid）。
- 临场变化订阅消息。

### 8.2 必须先解决的决策（阻塞 PRD 推进）

| ID | 决策 | 选项 | 默认建议 |
|---|---|---|---|
| Q1 | v1 是否包含真实付费？ | (a) 是，对接微信支付 (b) 仅"付费码"兑换，靠运营手动发码 (c) 全开放 | (b) 付费码 — 工程量小，链路真实可练 |
| Q2 | 访客能看到什么？ | (a) 只看赛事列表 (b) 看列表 + 简单胜负倾向 (c) 看完整公开摘要 | (b) — spec 默认且符合冷启动 |
| Q3 | 缺证据时主判断怎么显示？ | (a) 不显示，写"信息不足" (b) 显示但加"低置信"标 (c) 不显示主判断，只显示证据列表 | (a) — 最干净，符合 R2 |
| Q4 | v1 是否同步交付小程序？ | (a) 是 (b) 否，纯 Web | (b) — 单人节奏 |
| Q5 | OSINT 后端拆分要做到什么粒度？ | (a) 完整 spec 10 模块 (b) 最少：分出 factors / analysis / adapters (c) 不动 | (b) — 风险/收益最优 |
| Q6 | 6 维快捷追问要 LLM 接入吗？ | (a) LLM 路径 (b) 维度模板路径 + 证据筛选 (c) 二者结合 | (c) — 模板兜底 + LLM 增强 |

### 8.3 未解决的问题（不阻塞，但要在阶段 2-3 回答）

- 邀请码批量发放策略（是 admin 后台还是 CLI 脚本）？
- 付费码定价（单次 vs 月度 vs 永久）？
- 数据保留策略（用户提问历史保留多久）？
- 何时开始接入 osint-network 已有的情报数据（现状是独立采集）？
- 已付费用户的预测请求并发上限是多少？
