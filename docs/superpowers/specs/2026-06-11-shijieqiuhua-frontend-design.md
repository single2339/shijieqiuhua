# 世界球花前端设计规格

日期：2026-06-11

## 目标

将现有足球预测应用升级为“世界球花”：一个微信小程序优先、Web 增强的足球情报预测产品。

核心体验不是单纯预测胜负，而是围绕每场比赛持续问答。用户可以快速查看默认赛前判断，也可以继续追问半场、红黄牌、角球、进球数、球员状态、临场风险等具体问题。

## 设计假设

- 用户主要在微信里快速查看今日赛事，因此小程序体验优先。
- Web 端用于更深的研判、连续分析多场比赛、查看历史报告和复盘，不强行复刻小程序布局。
- Web 和小程序必须共享同一个用户体系。未登录用户只能看到公开的简单胜负倾向；登录用户才能获得完整分析权限。
- 产品不使用市场价格模型，不输出保证式结论；界面文案使用“倾向、压力、风险、证据强弱”等表达。
- 小程序分享和订阅消息必须遵守微信平台约束：分享由用户触发，订阅消息需要用户主动授权。

## 品牌方向

品牌名：世界球花

定位：有记忆点的足球情报助手，而不是冷冰冰的赛果预测器。

视觉方向采用“绿茵纸感”：

- 主色：深绿，用于品牌、主判断卡、关键按钮。
- 辅色：草金，用于可信度、概率环、重点提示。
- 背景：暖纸色，降低体育数据产品的冰冷感。
- 字体：沿用当前 Web 技术栈里的高质量无衬线字体方向，中文界面保持清晰、紧凑、可信。
- 图标：正式实现时使用已有 `@phosphor-icons/react` 或跨端可复用的本地图标，不使用 emoji 作为产品 UI。

## 信息架构

### 微信小程序

小程序采用 4 个底部 Tab。

1. 今日
   - 默认首页。
   - 展示今日和明日重点赛事。
   - 未登录用户每场只显示简单胜平负倾向和登录提示。
   - 登录用户每场显示比赛问答卡摘要：默认倾向、可信度、风险数量、可追问入口。
   - 提供联赛、时间、关注状态筛选。

2. 情报
   - 聚合所有比赛相关信号。
   - 分类包括伤停、战意、赛程、地理体能、裁判、天气、舆情。
   - 支持从情报信号跳转到受影响比赛。

3. 报告
   - 登录后保存用户生成过的问答结果和赛前长报告。
   - 支持收藏、赛后复盘、分享海报。

4. 我的
   - 承载登录、账号绑定、退出登录。
   - 管理关注比赛、订阅提醒、邀请权益、账户偏好。
   - 放置免责声明和产品边界说明。

### Web

Web 端使用同一套数据模型，但布局升级为工作台。

- 左栏：赛事队列，展示联赛、时间、关注状态、风险变化。
- 中栏：宽屏版比赛问答卡，展示默认判断、维度评分、证据摘要。
- 右栏：Ask 面板，保留用户问题历史、推荐追问、证据引用和报告生成入口。
- 未登录 Web 访客只看到赛事列表和简单胜负倾向；完整 Ask 面板、证据和报告入口显示登录门槛。

## 用户体系与权限

### 统一账号模型

Web 和小程序共用一个后端用户体系。前端不把“Web 用户”和“小程序用户”视为两套身份。

建议模型：

- `user`：内部用户主表，保存用户 ID、昵称、头像、创建时间、权限等级。
- `identity`：第三方或本地登录身份表，保存登录提供方、`openid`、`unionid`、手机号、邮箱等可绑定身份。
- `session`：服务端登录态，用于 Web 和小程序访问 API。
- `entitlement`：用户权限，控制完整分析、历史报告、订阅提醒、分享海报等能力。

小程序登录：

- 小程序端调用 `wx.login()` 获取临时登录凭证 `code`。
- 服务端使用 `code2Session` 换取 `openid`、`unionid` 和 `session_key`。
- 服务端根据 `openid/unionid` 找到或创建内部 `user`，再签发业务登录态。
- `session_key` 只留在服务端，不下发给小程序或 Web。

Web 登录：

- Web 端支持手机号/邮箱登录作为基础方案。
- 如果接入微信开放平台网站应用，可支持微信扫码登录。
- 当 Web 登录身份与小程序身份具备同一 `unionid`，或用户主动验证同一手机号/邮箱时，合并到同一个内部 `user`。

### 权限分层

未登录访客：

- 可查看今日赛事列表。
- 可查看每场比赛的简单胜平负倾向。
- 可看到少量公开摘要，例如“主队方向略优”。
- 不能使用自由提问。
- 不能查看完整证据、风险拆解、历史报告、收藏、订阅提醒。

登录用户：

- 可使用比赛问答卡的自由输入。
- 可点击半场、红黄牌、角球、进球数、球员、风险等快捷问题。
- 可查看证据强弱、风险提示、可信度等级。
- 可保存报告、收藏比赛、跨端同步历史。
- 可触发分享海报生成。
- 可在主动授权后订阅临场变化提醒。

权限不足状态：

- 被限制内容不直接隐藏为空白，而是展示简短预览和明确登录入口。
- 登录提示文案要说明用户将获得什么，例如“登录后查看角球、红黄牌和完整证据”。
- 不使用恐吓或诱导式文案。

## 核心组件

### MatchQuestionCard

比赛问答卡是“世界球花”的核心组件。

未登录状态下，`MatchQuestionCard` 降级为公开摘要卡，只展示比赛信息、简单胜平负倾向和登录入口。登录后展示完整问答卡。

结构：

1. 比赛头部
   - 联赛、开赛时间、主客队。
   - 显示中立场、天气、临场风险等状态。

2. 默认主判断
   - 默认展示胜平负或方向倾向。
   - 展示可信度分数、评级和风险提示。
   - 仍保持快速浏览能力，避免用户必须先提问才获得价值。

3. 继续问输入框
   - 标题为“继续问这场比赛”。
   - 输入框自动绑定当前 `match_id`。
   - 用户无需重复描述比赛上下文。
   - 支持自由问题，例如“上半场角球会不会偏多？”。

4. 快捷问题 chips
   - 半场
   - 红黄牌
   - 角球
   - 进球数
   - 球员
   - 风险

   这些 chips 是分析维度入口，不是投注玩法承诺。点击后生成带上下文的问题，并提示用户可继续编辑。

5. 证据摘要
   - 显示强证据、弱信号、样本不足三类内容。
   - 每条证据保留来源或来源类型。
   - 结论必须能解释“为什么”。

### EvidenceStrength

用于统一展示证据强弱。

- 强证据：多源一致、近期、直接影响比赛。
- 弱信号：单源、间接影响、样本较小。
- 样本不足：当前无法支撑明确结论。

### SharePoster

用于生成可分享的赛前卡片。

必须包含：

- 比赛双方和开赛时间。
- 用户问题或默认主判断。
- 可信度等级。
- 关键证据和风险提示。
- “世界球花”品牌名。
- 产品边界说明：情报研判，不保证结果。

### AuthGate

用于统一处理登录门槛。

- 包裹自由提问、完整证据、历史报告、收藏、订阅等登录能力。
- 在小程序端触发微信登录流程。
- 在 Web 端打开登录面板。
- 登录成功后回到用户原本要执行的动作，不丢失问题输入内容。

### AccountStatus

用于展示当前账号状态。

- 未登录：显示“登录后查看完整分析”。
- 已登录：显示头像、昵称、权限等级。
- 已绑定多端：提示 Web 和小程序历史会同步。
- 绑定冲突：提示用户选择保留或合并历史，避免静默覆盖。

## 数据流

1. 赛事数据
   - `match_id`
   - 联赛、球队、开赛时间、状态。

2. 用户身份
   - 未登录：匿名访客态，只允许访问公开摘要。
   - 已登录：服务端登录态，绑定内部 `user_id`。
   - 跨端身份：通过 `unionid` 或用户主动验证的手机号/邮箱进行合并。

3. 情报数据
   - 伤停、战意、赛程、地理体能、裁判、天气、舆情。

4. 用户问题
   - 自由输入或快捷 chips 生成。
   - 与当前 `match_id`、已有比赛情报、问题维度一起提交。
   - 未登录提交时先触发登录，登录后继续原问题。

5. 分析服务
   - 后端返回结论、可信度、证据、风险、报告正文。
   - 如果证据不足，返回“不确定”或“样本不足”，而不是强行给方向。
   - 服务端根据用户权限决定返回公开摘要或完整分析。

6. 展示和留存
   - 小程序展示问答结果。
   - 登录后报告页保存历史结果，并在 Web 和小程序间同步。
   - 用户可收藏、分享、订阅临场变化。

## 微信小程序约束

- 顶部导航必须避开微信右上角胶囊按钮和安全区。
- 底部 Tab 应通过小程序全局配置承载，保持原生预期。
- 分享能力由用户触发，分享卡片不应夸大确定性。
- 订阅消息只在用户关注比赛或点击提醒时请求授权，不做静默推送假设。
- 小程序登录使用 `wx.login()` 和服务端 `code2Session` 建立业务登录态。
- 小程序若绑定微信开放平台账号，可通过 `unionid` 与 Web 微信身份建立统一用户。
- `session_key` 属于服务端敏感会话材料，不下发到任何前端。

## 跨端实现边界

正式实现时不要把 Web 页面直接压缩成小程序页面。建议分层：

- 账号模型：内部 `user`、第三方 `identity`、登录 `session`、权限 `entitlement`。
- 领域模型：比赛、情报、问题、证据、报告。
- 领域组件：比赛问答卡、证据强弱、快捷问题、报告正文。
- 平台壳层：小程序导航、Web 工作台布局。

Web 端可先在现有 React/Vite 项目里完成品牌与组件改造。小程序端建议后续选择 Taro、uni-app 或原生小程序实现；本设计不强制技术栈，但要求共享接口契约。

## 成功标准

- 用户打开首页后，无需搜索即可看到今日重点赛事和默认判断。
- 未登录用户只能看到简单胜平负倾向和公开摘要。
- 登录后用户才能查看完整问答、证据、报告、收藏和订阅能力。
- 同一用户在 Web 和小程序端看到一致的历史报告与收藏状态。
- 用户能在首屏或接近首屏的位置继续追问当前比赛。
- 半场、红黄牌、角球、进球数等问题被作为核心入口呈现。
- 每个回答都能看到证据强弱和风险提示。
- 小程序和 Web 使用一致的数据语义，但采用不同布局。
- 分享和订阅能力符合微信平台约束。
- UI 不使用 emoji 作为正式图标，不出现保证结果或诱导式文案。

## 非目标

- 不在本阶段实现支付、会员、邀请返佣的完整商业化闭环。
- 不在本阶段实现复杂组织账号、团队协作或多角色后台。
- 不在本阶段承诺接入真实赔率、盘口或市场价格模型。
- 不在本阶段重构后端预测算法。
- 不在本阶段同时交付完整微信小程序代码。

## 后续实施建议

1. 先定义统一账号、登录态和权限 API 契约。
2. 改造现有 Web 前端品牌和核心比赛问答卡。
3. 抽出前端领域类型和组件边界，避免所有逻辑继续堆在 `App.tsx`。
4. 补充问题维度到请求结构，支持半场、红黄牌、角球、进球数等上下文。
5. 增加小程序适配设计稿或跨端技术选型。
6. 在有稳定接口后，再实现小程序端。
