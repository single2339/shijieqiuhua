# 世界球花 — 利益相关方分析

## 0. 上下文

这是一个**单人开发 + 私域邀请**的早期产品。"利益相关方"分析在这种规模下需要降维：传统企业项目里的"项目发起人 / 部门主管 / 法务 / 安全"等角色大多由同一个人承担。但即便如此，仍要把不同**身份**显式分开，因为同一个人在不同身份下的诉求会冲突，必须把冲突写明。

事实/推断/假设标记沿用上一阶段：`[F]` 事实、`[I]` 推断、`[A]` 假设。

### 2.1 四象限决策

| 象限 | 含义 | 成员 | 行动策略 |
|---|---|---|---|
| 高权高兴趣 | **紧密管理** | P1, P4, P6, S1, S2, S5 | 每次重大决策都要让这些"内化身份"参与；外部如 P1/P4/P6 通过提前对照规则、保留审计日志来"管理" |
| 高权低兴趣 | **维持满足** | (空) | 暂无 |
| 低权高兴趣 | **保持知情** | U1, U4, U5, S3, S4 | 提供反馈渠道、迭代日志、邀请码进度可见；用户调研重点对象 |
| 低权低兴趣 | **最小代价监控** | P2, P3, P5, U2, U3 | API/数据源监控、续费提醒、对 U3 明确不服务 |

### 2.2 P6（法律/监管）单独说明

虽然在矩阵里被画在"高权高兴趣"，但实际上 P6 是**反应式**的：只要不触发投诉或自动监控，它"不存在"；一旦触发，立刻成为最高优先级。所以策略是 **降低被触发概率** 而非"积极沟通"。具体动作：

- 文案审计：所有文案不出现"必胜""稳赢""推荐投注"等词。
- 用户协议 + 隐私政策：v1 上线前必须备齐。
- 不收集身份证、人脸、银行卡等敏感个人信息。
- 提供数据导出和注销渠道。

## 6. 给阶段 2 的输入

阶段 2（需求挖掘）需要带入的关键信息：

1. **冲突 C-1 解决方案**：必须用 MoSCoW 标注，不允许"全做"。
2. **冲突 C-3 已锁定**：缺证据 → 显示"信息不足"，所有需求条目必须遵守这条。
3. **决策 Q1（v1 付费形式）和 Q2（访客可见范围）**：在阶段 2 列需求清单时必须有明确答案；如果用户不决，本 PRD 用默认建议（Q1=b 付费码，Q2=b 列表+简单倾向）。
4. **干系人 U1 反馈渠道**：阶段 2 的 interview-design 要明确"5-8 个核心用户"是谁、怎么邀。
5. **平台约束 P1**：微信小程序的所有约束在 v1.5 前不影响 v1，但 PRD v1 的接口契约要为之做准备（账号模型、unionid 字段不能漏）。
